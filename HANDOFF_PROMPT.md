## What you are building

**Struq Voice.** A tray-resident Windows dictation app. Hold a key anywhere in Windows, speak,
release, and the transcribed text is pasted into whatever field you were focused on.

That single loop is the entire product. Everything else serves it.

Four qualities, in priority order. **Fast**: under one second from key release to visible text.
**Invisible until needed**: lives in the tray, never steals focus, never interrupts. **Accurate**:
Parakeet TDT locally by default, whisper.cpp on the GPU for hard audio, OpenRouter Whisper as an
opt-in cloud fallback. **Beautiful**: the capture overlay is seen dozens of times a day and should
be the nicest piece of UI on the machine.

Target platform is Windows 11 x64 only. The build machine has an RTX 4070 Ti, a Ryzen 7 7800X3D,
and 31GB of RAM, which is why the local-first default is realistic.

## The bar

This is the part that matters most, and the part most likely to go wrong.

The owner has explicitly rejected generic AI-generated interface work. That is the failure mode to
design against, and it is a real risk here because the stack includes shadcn/ui, whose default skin
is the single most recognisable look in current software.

**shadcn is in this stack for behaviour, not appearance.** Take Radix's focus management, keyboard
navigation, roving tabindex, portal and dismissal semantics, and ARIA wiring, all of which are hard
to get right and are correct out of the box. Then strip every default class and rebuild the
appearance from the tokens in `docs/assets/theme.css`. A generated component that has not been
restyled is not finished work.

The palette is **Velden Linen Forest**: a warm linen page, deep forest ink, one terracotta accent.
It is fully derived, contrast-verified and ready to use in `docs/assets/theme.css`. Copy that file
to `src/renderer/styles/theme.css` before building any UI, and style from tokens from the first
component onward rather than styling ad hoc and retrofitting.

Two rules govern every colour decision:

1. **Accent is for primary actions and moments of emphasis only.** One primary action per view.
2. **Interaction states are generated by brightness alone.** Lightness moves; hue and chroma never
   do. There is never a second colour hiding inside a hover state.

Section 8 of `DESIGN_SYSTEM.md` lists the anti-patterns that must not ship: gradient text,
glassmorphism, stacked shadows, sparkle icons, emoji, "Oops! Something went wrong", decorative
empty-state illustrations, and the rest. Read that list before you build, not after. Section 10 is
a twelve-question self-review to run before every UI commit.

Note two things that will feel counterintuitive if you build on autopilot:

- **Surfaces are lighter than the background.** Paper on linen, not panels on a dark canvas. This
  inverts the habit most component libraries encode.
- **Neither pure black nor pure white appears anywhere**, and no border is neutral grey. The warm
  page and cool ink are the whole character, and a grey hairline reads as dirt on it.

## Landmines already diagnosed. Do not rediscover these.

**1. `ELECTRON_RUN_AS_NODE=1` breaks every Playwright run started from a VS Code terminal.**
VS Code's extension host exports it into terminals it spawns. Inherit it and `electron.exe` behaves
as plain Node, rejecting Playwright's Chromium switch. You will see only
`Error: Process failed to launch!`, which looks exactly like an Electron/Playwright version
incompatibility and is not. It reproduces on Electron 39, 41 and 43, and it vanishes in a normal
terminal. The harness in section 7.1 of the plan strips the variable. If you ever see that error
again, confirm with a bare `electron.exe --remote-debugging-port=0 --version`.

**2. pnpm 10 skips native postinstall scripts** without `allowBuilds`. If
`node_modules/electron/path.txt` is missing after an install, the binary did not download: run
`node node_modules/electron/install.js`.

**3. `uiohook-napi` may stop firing after `getUserMedia`.**
[Issue #54](https://github.com/SnosMe/uiohook-napi/issues/54) reports the global keyboard hook
dying when a media stream is initialised while an Electron window is focused. The plan's hidden
recorder window should structurally avoid this, because the reported workaround is precisely
"allocate the stream while unfocused" and that window is never focused. **This is a hypothesis, not
a verified fact.** Prove it in Phase 2 with ten consecutive capture cycles while the main window is
focused, before building anything on top of it. Two fallbacks are named in the plan's risk table.

## Non-negotiable constraints

- **Never break focus.** The overlay is `focusable: false` and uses `showInactive()`, never
  `show()`. This is the single property that makes global paste work: because the foreground window
  never changes, a synthesised Ctrl+V lands where the user already was. If you find yourself
  calling `show()` on any window during a capture, you have introduced a bug.
- `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true` on every window. No
  exceptions.
- Every IPC channel and payload type is declared in `src/shared/ipc.ts` and nowhere else. The
  renderer never imports from `src/main/`. `src/shared/` has no side effects and no Electron
  imports.
- **Local transcription is the default.** Cloud is opt-in. No audio leaves the machine unless the
  user explicitly selected a cloud engine, and the router never auto-cascades from a local engine to
  a cloud one.
- Never commit model files, sidecar binaries, or audio recordings. Set the `.gitignore` up front.
- **No em dashes or en dashes anywhere.** Not in code, comments, UI copy, docs, or commit messages.
  Restructure the sentence rather than swapping in a hyphen. Scan your output before every response.
- Small, verifiable commits. One concern each. Conventional commit format.
